# SEO Claude Team

A fleet of AI agents that grow **Shopify revenue** for **Real Skin Care** (natural deodorants, body care, oral care, lip balm) on its storefront `realskincare.com`, using SEO as the means. RSC also sells on Amazon, where it shares a seller account with a sister brand, **Culina** (cast iron / Blackstone griddle care). Culina is on a separate website with its own SEO automation; this codebase's Shopify/content/SEO pipelines are RSC-only. The Shopify website is the primary revenue channel. Amazon is complementary and validates commercial intent for keyword/SEO decisions.

## Prime Directive — Revenue

**The purpose of this project is to generate revenue for Real Skin Care's Shopify store. SEO is the means, not the goal.** Every agent, report, and change exists to drive *traffic that converts to sales*. Traffic that doesn't convert, content with no purchase path, and rankings that don't produce revenue are not wins — they are unfinished work at best and wasted effort at worst. Before building or optimizing anything, answer: **how does this convert traffic to sales?** If it can't, it's a waste of time.

This reorders how every agent prioritizes:

- **Commercial pages first, but do not multiply them.** Collections and PDPs convert; informational blog posts mostly don't. **A collection exists only where a category holds 2 or more distinct products — single-product categories are PDP-only, and a collection is never created to chase a keyword.** Chasing rankings with new collections produced 62 live collections for 9 products, which split ranking signal and earned 51 clicks on 93,785 impressions in 90 days. Optimize the pages that exist before creating another.
- **Every page that earns traffic needs a conversion path** — a prominent above-the-fold link/CTA to the relevant collection or PDP, plus a working buy-box. A post with traffic and no buy path is a bug to fix, not a success.
- **Measure in dollars, not clicks.** `agents/seo-impact` attributes Shopify revenue to pages/clusters. A cluster with high clicks and $0 revenue (e.g. toothpaste ≈268 clicks / $0) is a top priority to fix or stop investing in — not a ranking to celebrate. **A $0 cluster is now put ON HOLD automatically** — see the cluster-hold section below.
- **CTR and conversion are first-class.** Impressions without clicks (low CTR) and clicks without purchases (no conversion) are the two revenue leaks. Closing them beats chasing new keywords.

When an agent has the data to make a revenue-improving decision, it makes it and applies it (see Autonomy Principle below).

## Development Rules (non-negotiable)

1. **Always work on a branch** — never commit directly to `main`. Use `feature/<name>` or `fix/<name>`.
2. **Always merge via pull request.** Open with `gh pr create`. No fast-forward, no squash-merge locally, no pushing to `main` from the feature branch.
3. **Test locally before pushing to the server.**
4. **Test a fix on one post before bulk-applying.** End-to-end (edit → upload → check live site) before writing batch scripts.
5. **These rules apply even for one-line fixes.**
6. **Never work in the main checkout — take a worktree.** Multiple sessions run against this repo at once, and two sessions sharing `/Users/seanfillmore/Code/Claude` fight over HEAD. This has cost real work twice: 2026-07-24 a session switched the shared working dir onto its branch mid-task and a commit landed on the wrong branch; 2026-07-27 two sessions committed to `feature/marketing-tactic-lifecycle` within the same hour, one of them opening a PR whose body was stale inside the hour.

```bash
scripts/new-worktree.sh <name> [branch-name]     # branches from origin/main, symlinks .env + node_modules
cd .claude/worktrees/<name>                       # commit and open the PR from here
git worktree remove .claude/worktrees/<name>      # after the PR merges
```

Branch from `origin/main`, never from wherever the main checkout is sitting — it is 40+ commits stale as often as not. Before committing anywhere, re-check `git branch --show-current`; never assume the branch you left is the branch you are on.

## Autonomy Principle

Agents that have the data to make a decision should make it and apply the change. Surface cases to the user only when genuinely ambiguous (cannibalization-resolver auto-applies HIGH confidence, queues MEDIUM/LOW for review; meta-ab-tracker auto-reverts losing variants). When designing a new agent, default to apply-not-dry-run for production behavior. See `~/.claude/projects/-Users-seanfillmore-Code-Claude/memory/feedback_autonomous_by_default.md` for the full rule.

## Architecture (non-obvious patterns)

**Single-file daily orchestration.** `scheduler.js` at the project root runs every day at 8 AM PT (15 UTC) on the production server via cron. It dispatches the daily pipeline, plus weekly jobs on Sundays and monthly jobs on the 1st. Read `scheduler.js` for the actual order.

**Deferred-notification digest.** Agents call `notify({...})` from `lib/notify.js`. **Every** notification appends to `data/reports/daily-summary/YYYY-MM-DD.jsonl` rather than emailing — `status: 'error'` only changes how the digest renders the row, it does not escalate. The single exception is `immediate: true`, which emails at call time; use it sparingly. The `daily-summary` agent reads the JSONL at 5 AM PT and sends one consolidated HTML digest via Resend. `NOTIFY_DEFERRED=1` is set by `scheduler.js` and by the giveaway cron entry but is **read nowhere** — deferral is unconditional and the variable is vestigial. This paragraph previously claimed errors bypassed deferral; they never have, so anything that must not wait for the 5 AM digest needs `immediate: true`.

**Content pipeline order:** `content-strategist` → `content-researcher` → `blog-post-writer` → `image-generator` → `answer-first-rewriter` → `featured-product-injector` → `schema-injector` → `editor` → `publisher`. Orchestrated by `calendar-runner` (reads `data/calendar.json`).

**Cannibalization auto-publish flow:** the `cannibalization-resolver` runs Sundays. CONSOLIDATE actions merge content via Claude → run editor → if editor finds no blockers (no `meta.needs_rebuild` set), the merge auto-publishes and the redirect is created immediately. If the editor flags blockers, the merge is HELD — draft saved, live winner untouched, surfaced in the report's "Drafts needing review" section — and **the redirect is not always created**: `agents/cannibalization-resolver/redirect-decision.js`'s `decideHeldMergeRedirect` still creates it when the loser's own GSC clicks (from the window already fetched for detection, no extra call) are provably zero, and skips it — same as before — when the loser earns real clicks, or when traffic data is missing (fails safe). This exists because "skip while held" used to be unconditional and a held merge has no expiry: the tattoo-soap merge sat held six days (2026-08-16 to 2026-08-22) on "overall quality: needs work" while its 0-click loser kept splitting ranking signal from a 10-click winner, until an operator redirected it by hand. **That hold turned out to be right for the wrong reason, and investigating it on 2026-08-22 found two independent defects, both now fixed.** (1) The merge itself was **truncated** — `consolidateContent` ran at a flat `max_tokens: 8000`, below the *median* article's own ~6.6k tokens once the prompt's "+30% length" allowance applies, so most merges were destined to truncate, not just this one. It returned HTML ending mid-sentence ("…fragrance-free (or scented"), having dropped the CTA, Sources, Related Articles and 3 FAQ entries. Nothing checked `stop_reason`. The ceiling is now derived from the winner's own length (`mergeMaxTokens`) and `assertHtmlComplete` runs on the result, so a truncated merge throws instead of becoming a publishable draft. (2) The hold reason was an artifact: the editor reconciles Overall Quality into the report it saves (`reconcileOverallQuality`), then derived `meta.needs_rebuild` from the **raw pre-reconciliation** LLM text — so the saved report read "OVERALL QUALITY: Pass" while the flag gating auto-publish read "overall quality: needs work", and no reader of the report could see why it was held. The gate now reads the same reconciled text everything else reads (`llmBlockerReasons`). Note the order these interact: fixing (2) alone would have **auto-published the truncated merge** over a live ranking page. The editor's LLM had explicitly asserted "Final section (FAQ) is complete, not cut off" about content that was cut off mid-word — an LLM assertion is not a check, which is why truncation detection is deterministic and lives in `lib/html-output-guards.js`. An earlier version of this paragraph said "Redirects always created" with no carve-out mentioned at all; an agent read that and shipped a redirect the resolver's actual code would not have made on its own — right call on the evidence, wrong premise. `--publish-pending-drafts [--apply]` clears any backlog of drafts the agent created on prior runs (it does not itself create the loser redirect on publish — that still only happens on the run that decided the merge).

**Optimization Queue auto-apply.** `agents/queue-autoapply` (scheduler step 4d, daily, `--apply` on the scheduled path and dry by default on the CLI) drains `data/performance-queue/` without a human clicking Approve — the queue had reached 21 pending items, the oldest 37 days old, and work that sits in a queue earns $0. Policy lives in the pure `lib/queue-autoapply.js`: it **applies** `seo-opportunity`, `quick-win`, `flop-refresh`, `page-meta-rewrite`, `low-ctr-meta` and `legacy-flop` after the existing editorial gate (`lib/edit-gate-repair.js`) passes — a blocked item goes into that library's repair loop and stays `pending`, it is never escalated to a human list — and **auto-dismisses** `collection-gap` items that hold fewer than 2 distinct products or sit in a cluster `data/reports/seo-impact/latest.json` shows earning $0 (`lib/cluster-revenue.js`'s `classifyClusters`). **No cluster name appears in the code**; only the 2+ products rule is hardcoded, because it is the Prime Directive and must keep working when the revenue report is stale or missing. A collection-gap that passes both gates is still never auto-created — creating a commercial page is the decision that produced 62 collections for 9 products. **At most 5 live applies per run**, oldest first; dismissals are uncapped because they touch only a local JSON file. It applies **directly** rather than only stamping `approved`: the publisher's `publishApprovedQueueItems()` runs inside `agents/publisher/index.js`'s `main()`, which requires a post-metadata argument, so `approved` items only ship on days the calendar happens to publish something — leaning on that seam would have swapped a manual chore for a silent stall. The actual publish path is `lib/queue-apply.js`, shared with the dashboard's Approve route so the collection-gap gates (2+ products, `published: false` draft, `validateCollectionSpec`) cannot exist on one path and not the other; Shopify functions are injected there and in `lib/queue-revert.js` because `lib/shopify.js` throws at import time without OAuth credentials. Nothing is applied without a backup captured **before** the write and a `revert_plan` stamped on the item, and a refresh with no backup is refused outright rather than overwriting a live article irreversibly.

**$0 clusters go ON HOLD — "if it doesn't drive revenue, we put it on hold" (Sean, verbatim) — but only when TWO sources agree.** A hold means **stop spending unattended LLM/refresh cycles on a cluster**. It does **NOT** mean unpublish, delete, redirect, deindex, or drop from a sitemap: these are live, indexed pages, they stay live and keep whatever traffic they have, and nothing on this path may call `lib/post-kill.js` or create a redirect (pinned by a test). The trigger was 2026-08-21, when one $0 cluster took 11 of 15 indexing "critical" slots and fired 11 content-quality refreshes — each a chain of paid LLM calls — on pages that have never produced a dollar. **The rule lives in `lib/cluster-hold.js` and names no cluster in its logic.**

**`seo-impact` alone is NOT sufficient evidence for this decision, and the first version of this rule got it wrong because of that.** Its organic-attributed revenue is directional only and must be reconciled against Shopify orders (documented here and in `reference_order_level_attribution.md`) — held on that source alone the rule paused the **soap** cluster, which really sells **$430.70 / 90d, 19% of all revenue, second only to lotion**. `seo-impact` filed only $62.40 of that under `hand soap` and showed `soap` at $0; the rule read an attribution artifact as a verdict. So a cluster is held **only when BOTH** agree it earns nothing: (1) `lib/cluster-revenue.js`'s `classifyClusters` says `proven_dud` — $0 attributed with ≥100 clicks across ≥5 pages — **AND** (2) measured product revenue from `data/snapshots/shopify/*.json` `topProducts[]` is **below one average order in EVERY corroboration window**. That floor is derived from the same snapshots (window revenue ÷ window orders), not a constant, so it moves with the business instead of ageing into a wrong number; a category that has not produced even a single average order in the window is materially not a channel. **Unanimity is required** — one window showing material revenue blocks the hold, because a quiet 28 days is not evidence that a category earns nothing.

The two windows are the report's **own** `window` block (so "the same window" is literal, not a constant that quietly stops matching) plus a **90-day** window ending on the same day; the report window carried 18 orders, too thin to condemn a slow mover on its own. The two vocabularies meet through `lib/keyword-index/cluster.js`'s ordered `assignCluster`, applied to **both** sides — that is what lets `seo-impact`'s split `soap`/`hand soap` rows be compared against product titles that know nothing of the split, and its first-match ordering (soap before lotion) is the only reason "Moisturizing Coconut Soap" counts as soap revenue rather than lotion revenue.

**Disagreement is a finding, not a shrug.** When `seo-impact` says $0 and the orders say otherwise, the cluster is **NOT held** and the mismatch is reported loudly — in `holdBanner()`, in `npm run cluster-holds`, and (because these agents run unattended) as `renderDisagreementLines()` in each gated agent's **digest body**. It means attribution is broken for that cluster, which is worth fixing in its own right.

**Everything fails OPEN.** Missing report, missing snapshots, a window with no orders, a cluster name that maps to no product family, or any day at `agents/shopify-collector`'s top-5-products-per-day cap (which makes the window a lower bound, so a zero could be the part that was cut — it has never happened, max 4 across all history) → **nothing is held**, and the reason is printed. Pausing the fleet on an absent measurement is the opposite of the Prime Directive. `agents/queue-autoapply` reads the same loader (it used to classify the report inline), so the queue's $0 collection-gap dismissal and the refresh hold can never drift apart.

Gated — the five points that actually spend money unattended, each **skipping and counting**, never silently dropping: `agents/indexing-fixer`'s `crawled_not_indexed` → content-quality refresh (the 11/day), `agents/performance-engine`'s four pickers, `agents/legacy-rebuilder`'s pick list, `agents/blocked-post-resolver`'s candidates, and `agents/refresh-runner`'s three bulk pick lists. **The hold is always applied BEFORE the per-run cap** — holding afterwards would let five held posts eat a budget of five and leave every earning-cluster post untouched, which is the bug this rule exists to prevent wearing different clothes. Deliberately NOT gated: indexing-fixer's Tier 1/Tier 2 (a sitemap ping and an Indexing API submission cost nothing but a Google quota, and a hold is never a deindexing — held pages stay submitted); `agents/content-refresher`, which is never on cron and is only ever reached with an explicit `--slug` from a caller already gated above; and any single-slug CLI invocation anywhere, because a hand-typed slug is not unattended spend. Every gated agent reports its held count in the console, in its `renderHoldLines()` digest body and in its `notify()` subject — one **deferred** notification, never `immediate: true`, and a hold never sets `status: 'error'`, because it is the policy working rather than a failure. Two agents that would otherwise fall silent (`performance-engine`, `refresh-runner`) fire a notification specifically for the "did nothing BECAUSE everything was held" run: a hold nobody can see becomes a mystery outage six weeks later.

Observable and overridable: **`npm run cluster-holds`** (`scripts/cluster-holds.mjs`, `--json` for machines) prints every cluster side by side as **attributed $ vs real order $**, its product family, its state (`ON HOLD` / `DISAGREE!` / `no data` / `earning` / `unproven`), and the agents that honour the hold. The `ORDERS $` column is per **family**, so sibling clusters legitimately repeat the same figure. **`--include-held`** on any gated agent runs the held items anyway and still records that they were held. As of the 2026-08-22 report exactly **one** cluster qualifies — **toothpaste** ($0 attributed on 663 clicks / 24 pages; $0 real orders over the 28d window and $39.00 over 90d, both under one average order). **Soap is NOT held**: $0 attributed but $156 / $365.70 in real orders — it is the standing attribution disagreement the tooling reports. `lotion` ($0 attributed / 56 clicks) is `unproven`. `agents/performance-engine` also gained the standard `isDirectRun` guard in the same change — importing it used to run the whole nightly agent.

**Closed-loop agent feedback.** Agents write reports to `data/reports/<agent>/`. `insight-aggregator` reads them, extracts recurring patterns, writes per-agent guidance to `data/context/feedback.md` under `## <agent-name>` headings. Each agent reads its section at startup and incorporates it into its LLM prompt. The `editor` also reads `data/context/writer-standing-rules.md` so what the editor flags becomes what the writer avoids.

**Demand mining — top-of-funnel questions voice-of-customer structurally can't reach.** `agents/demand-miner` runs monthly, immediately after `voice-of-customer` in the same scheduler block — it reads `data/context/personas.json`, which `voice-of-customer` rewrites in that same run, so running it first would seed from last month's personas. The pure logic lives in `lib/demand-questions.js` (no I/O, same split as `lib/voice-of-customer.js`, testable without stubbing): it seeds Google People-Also-Ask + related-search harvesting from two empirical sources — GSC impression leaks and persona objections — under a hard `SEED_CAP` of 40, because each seed is one paid DataForSEO SERP call made unattended from cron, and an uncapped run turns a bad GSC week into hundreds of unauthorized calls. `--limit <n>` (read in the shell, not a change to `SEED_CAP`) trims a run to fewer seeds for a cheap rehearsal, clamped so it can never raise the cap above 40. The cap is split as a **reserve per origin** (`LEAK_RESERVE`/`PERSONA_RESERVE`, 20 each), not a single ordered slice: a real production run yielded 253 impression leaks against the 40-seed cap, and taking leaks first would fill the whole budget from leaks alone — starving `persona_objection` to zero and leaving `persona_id` null on every question, silently breaking the join to `personas.json` on `stage` + `persona_id` that this artifact exists for. That same join is why `AWARENESS_LEVELS`, the five-stage funnel vocabulary, is **imported from `lib/voice-of-customer.js` in `lib/demand-questions.js`, never redefined** — a second copy would drift and break the join the same way. Persona objections stay lotion+soap only by construction (`personas.json` IS voice-of-customer's `SKIN_CLUSTER_HANDLES` research), but GSC leaks are unfiltered site-wide queries — `lib/demand-questions.js`'s `filterLeaksToSkinCluster` (reusing `lib/keyword-index/cluster.js`'s ordered `assignCluster`, not `voice-of-customer.js`'s handle-based `filterSkinCluster`, which doesn't fit free-text queries) keeps only `SKIN_LEAK_CLUSTERS`-cluster leaks before `deriveSeeds` ever sees them — `lotion`, `soap`, `coconut oil`, `deodorant` and `lip balm`, always excluding `toothpaste` (≈268 clicks / $0 revenue, Prime Directive) and `hair` (RSC sells no hair products) — because roughly a third of a real leak report's top entries were oral-care queries (e.g. "coconut oil as toothpaste") that would otherwise be mined on a paid budget for a cluster that already earns $0. The artifact's `clusters` field (sourced straight from `SKIN_LEAK_CLUSTERS`, never hardcoded) is an **array**, not the single `cluster: "skin"` string this used to stamp: deodorant and lip balm were added to the leak-mineable set on 2026-08-22, and no one-word label describes lotion+soap+coconut-oil+deodorant+lip-balm honestly. That array only bounds leak-origin seeds, though — persona-origin seeds stay lotion+soap regardless of what `clusters` lists, so a reader has to check each question's own `seed_origin`, not the header, to know which scope actually produced it. Both `demand-questions.json` and `demand-questions.md` carry that caveat inline rather than assuming a reader works it out. `demand-miner` is also the **fifth reader** of `personas.json` (`realApplyPersonaOverlay`): it applies `data/context/operator-angles.json`'s overlay before `sanitizePersonas`, same order and same reasoning as the other four readers documented under `data/context/operator-angles.json` below — skipping it would let a retired persona angle keep consuming a paid seed while an operator-authored replacement is never seeded. The agent refuses to write `demand-questions.{json,md}` when a run produces zero questions, leaving the previous artifact in place: this covers both "every seed's SERP call failed" and the more dangerous case where every call succeeded but returned no PAA/related-search items, which would otherwise look like a clean run while silently replacing good data with nothing. The one Claude call classifying every harvested question by funnel stage merges its response back onto records **positionally, by the `[n]` index the prompt assigns** — never by echoing question text, which broke on a curly apostrophe, a retained `[n]` prefix, or collapsed whitespace — and retries once on malformed/schema-invalid output (so "one Claude call" is up to two per run), but a `stop_reason: 'max_tokens'` response throws immediately without retrying, because truncated JSON cannot become valid on a second attempt against the same ceiling. Upstream, `lib/dataforseo.js`'s `getSerpResults` now also returns `paa` and `relatedSearches` alongside the original `organic`/`serpFeatures` — **additive only**. Its item-shaping logic was extracted into an exported pure `extractSerpPayload(items)` so it's testable without a network call, and all nine existing production callers destructure only `organic`/`serpFeatures` off the same return object, so they are unaffected. `agents/gsc-query-miner` writes `data/reports/gsc-query-miner/impression-leaks.json` on **every** run, including empty ones, so a consumer's staleness guard can tell "ran, found nothing" from "did not run" — the same reasoning `untapped-candidates.json` already documents.

**Publish state has one source of truth, because "no status" is not "not published".** `lib/post-publish-state.js` (`resolvePublishStatus` / `isLivePost` / `isLiveOrScheduled`) answers "is this post live?" for the whole fleet. **52 of 93 posts carry a `shopify_article_id` and no `shopify_status` key at all** — the legacy corpus, synced in by `scripts/sync-legacy-posts.js` without ever passing through `agents/publisher`, which is what stamps that field. Every consumer requiring a strict `shopify_status === 'published'` therefore treated live, indexed, traffic-earning pages as unpublished: `post-performance`, `refresh-runner`, `publish-drift` and `draft-refresher` could not see them at all, and the 5 AM digest reported three of them as "Action Required — hard-blocked" every morning from 2026-08-16 while all three returned HTTP 200. The helper is deliberately **not a third rule** — it is the inference `agents/indexing-checker` and `agents/legacy-triage` had each already hand-rolled (explicit status wins; otherwise an article id plus a parseable publish date decides published vs scheduled), written once. `'unknown'` is returned rather than guessed, and callers must treat unknown as not-live. **The real fix is `scripts/backfill-shopify-status.mjs`** — it asks LIVE Shopify per article and writes the true status down (dry by default, `--apply` to write). Shopify has no `status` field on an article: `published_at` is the whole story (null = draft, future = scheduled, past = live). A 404 writes **nothing** — a deleted article is not a draft, and stamping it as one buries the real problem under a plausible field. The helper is the safety net for whatever the backfill cannot resolve, and for posts synced in later.

**Hard-blocked posts resolve themselves.** `lib/blocked-posts.js` holds the one pure `classifyBlockedReport` rule, shared by the digest, the dashboard card and `agents/blocked-post-resolver`; it moved out of `agents/dashboard/lib/data-loader.js` (which drags in the whole dashboard path tree and is not importable from an agent, though it still re-exports the function so existing callers are unchanged). Two audiences, one rule, split by **`includeLive`**: the 5 AM email passes `false` — a live page is never an "Action Required" row, because the resolver owns fixing it and reports its own outcome into the same digest — while the dashboard and the resolver pass `true`. Explicitly-published and inferred-published posts now get **identical** treatment there; the old split (skip explicit `published` outright, let an unset status fall through to the freshness rule) is precisely what made the 52 legacy posts behave differently from the other 41. `agents/blocked-post-resolver` runs daily from `scheduler.js` right after `legacy-rebuilder`, capped at 5 posts (each is a chain of paid LLM calls). It does not reimplement repair: it schedules `scripts/remediate-live-post.js <slug> --push`, which already pulled the live body, gated it, repaired up to 3× and pushed only a PASSING revision — and was simply never on a timer. What it adds is what happens when that loop runs out: **soften, never delete.** It forces a `citation-finder` softening pass, re-gates, pushes if that cleared the gate, and otherwise clears `needs_rebuild` and leaves the page LIVE. It never calls `lib/post-kill.js` and never unpublishes — these are indexed pages that earn traffic. A written-off post stamps `meta.blocked_resolution.report_fingerprint` (a content hash of the editor report, **not** an mtime — file mtimes under `data/posts/` are pull/checkout times, not review times), so tomorrow's run does not pay to fail again on identical text while a genuinely new editor verdict re-opens it automatically. Two leaks that made a blocked post immortal are closed alongside it: `agents/legacy-rebuilder`'s `broken` bucket returned success **without** clearing `needs_rebuild`, so `findLegacyPosts()` re-queued the same post daily forever (the `winner` branch had always cleared it), and `agents/content-remediator`'s link-drop guard threw and gave up on the first sample — it now gets **exactly one** retry with the missing anchors named in the prompt (`lib/content-revision.js`), while the guard itself stays hard: a second sample that still drops a link is still never saved, and only the link-drop failure is retryable (retrying a `max_tokens` truncation against the same ceiling cannot succeed).

**Giveaway confirmation has TWO mechanisms and they disagree about every entrant at once.** `config/giveaway.json`'s `confirmMechanism` is the switch, and `lib/giveaway/reconcile.js`'s `resolveMechanism` is its only reader — an unrecognised value **throws** rather than defaulting, because a typo resolving to whichever branch happens to be the default silently rewrites the entry ladder for the whole promotion. Under **`double_opt_in`** (the launch behaviour, still live as of 2026-08-23) Klaviyo only adds a profile to the list once the opt-in link is clicked, so membership of the SUBSCRIBED set **is** the confirmation. Under **`flow_link`** the list is single opt-in, the entrant is subscribed the instant they submit the form, and a branded flow email carries the link instead (Klaviyo's `update_property_link`, writing `gv_confirmed`) — so subscription proves **nothing**, and reading it as confirmation pays the advertised +2 to every submitter *and* inflates every §5 referral rung with it (§5 pays "+5 per confirmed friend"). `p.subscribed` as a synonym for "confirmed" had been copied into six places; they all now go through `confirmedEmailSet`, and a seventh copy is a bug, not a shortcut. Two records are deliberately **mechanism-independent** — the `gv_confirmed_at` stamp and a legacy `gv_breakdown.confirmed` — because they are what carries an already-confirmed entrant across the cutover and what makes a rollback cost nobody their +2; the draw (`lib/giveaway/draw-snapshot.js`) keys off the stamp alone and needs no change either way. `gv_confirmed` is compared against the **string** `'true'` as well as the boolean: `update_property_link` takes its value as a quoted literal, so a `=== true` test passes every unit test written with a boolean fixture and rejects every real confirmation. Two traps worth naming: `scripts/giveaway/nudge-unconfirmed.mjs` **refuses to run** under `flow_link` (re-issuing a subscribe to a single opt-in list sends no email at all, so it would report "nudged 40" while sending zero and burn each profile's nudge cap), and the nurture flow triggers on **list-add**, which under `flow_link` means "submitted" rather than "confirmed" — it must be re-triggered off the confirmed segment first, or `01-confirm` opens by congratulating people who never clicked. Klaviyo's own double opt-in email is why the cutover exists at all: its subject line and button label **cannot be edited**, so the two elements that earn the click could never mention the prize. Full runbook, including the four steps only the Klaviyo UI can perform, in `docs/giveaway-confirm-cutover.md`.

**Dashboard.** `agents/dashboard/` is a Node app (PM2 process `seo-dashboard`, port 4242). Browser HTML/CSS/JS lives in `agents/dashboard/public/` — edited directly, no template literal escaping rules apply.

**Dashboard route contract — three rules, because a bad request used to kill every tab.** `agents/dashboard/lib/router.js`'s `dispatch()` calls handlers without awaiting them, and `seo-dashboard` is a single shared PM2 process on a public URL, so before hardening any uncaught throw or rejection was fatal to the whole process. Now: (1) `dispatch()` catches **both** a synchronous throw (try/catch around the call) and an async rejection (`.then(undefined, ...)` on whatever the handler returns) and answers a fixed `500 {"ok":false,"error":"internal error"}`, never echoing the exception — neither arm substitutes for the other, since the try/catch can't see a rejection and the `.then()` can't see a throw with no promise yet. That makes **returning** the promise load-bearing: a handler that fires an async call without `return`ing it hands `dispatch()` nothing to attach to. This was a live bug in `agents/dashboard/routes/agents.js`, whose handlers now `return ctx.runAgent(req, res)` / `return ctx.bgRunStart(req, res)`. (2) Every route module that reads a request body now reads it through `await readJsonBody(req, { maxBytes })` from `agents/dashboard/lib/responses.js` — `grep -rn "req.on('data'" agents/dashboard/` returns only that one file, everywhere else in the tree — and that includes `agents/dashboard/lib/run-agent.js`, not just files under `routes/`. The cap is per-call, not a shared constant: `DEFAULT_MAX_BYTES` is 1 MB for the authenticated routes, but the two unauthenticated ones keep their own smaller ceilings — `/api/rum` 8 KB, `/api/giveaway/*` 4 KB, the giveaway upload `MAX_UPLOAD_BASE64 + 2048` — because a shared 1 MB default would have silently raised the limit on the routes that most need one. `readJsonBody` also takes `destroyOnOverflow` (default `true`, which just preserves prior callers' behavior); `giveaway.js` passes `false` and defers the destroy to `res.on('finish', ...)`, because destroying the socket before the 413 flushes makes nginx serve the entrant a bare 502 instead — pinned by `tests/dashboard/giveaway-routes.test.js:182`. (3) `agents/dashboard/index.js` wires `agents/dashboard/lib/fatal-reporter.js` to `unhandledRejection`/`uncaughtException` as the last-resort net: it logs, calls `notify({ immediate: true, ... })`, and **keeps serving** — no exit, no restart. Its firing is a bug report, not a routine event, and it's hardened against its own failure modes (a rejecting `notify`, a hostile `err` object) because during this work the net itself found three separate ways to become the outage it exists to prevent. **Never do work in a callback whose promise the handler does not return.** `req.on('end')` is the clearest case — it runs on the emitter's stack, outside the handler's promise, where the `dispatch()` guard cannot reach it — but multer's callback-style API is the same shape: `ctx.upload.*(req, res, callback)` does its work inside `callback`, not inside whatever the route handler itself returns, so `dispatch()` has nothing to attach to there either. That unreachability, not `null` bodies, is why every body-reading route module was migrated onto `readJsonBody`. The three multer routes in `routes/creatives.js` are the exception to the single-reader rule, each guarded by its own multer error argument instead of `readJsonBody`: `/api/creatives/templates/from-image` (`ctx.upload.single('image')`, an `async` callback, reads `req.file`), `/api/creatives/reference-images` (`ctx.upload.single('image')`, a sync callback, reads `req.file`), and `/api/creatives/generate` (`ctx.upload.array('referenceImages', 20)`, an `async` callback, reads `req.body`/`req.files`) — all three carry the shared multer instance's 20 MB `fileSize` limit rather than `readJsonBody`'s byte cap.

**Shopify API version — one constant, because a stale pin does not fail, it lies.** `lib/shopify-api-version.js` holds `API_VERSION` for the whole fleet (currently **`2026-07`**, the current stable quarterly). Everything that builds an admin URL imports it: `lib/shopify.js`, `agents/technical-seo`, `agents/apply-optimization`, `agents/meta-ab-tracker`, and the ~20 standalone `scripts/*` that hand-roll their own `fetch`. It is deliberately a **separate module from `lib/shopify.js`** — that file reads `.env` and throws at import time without OAuth credentials, so scripts authenticating differently could not reach the constant through it; this one reads nothing and has no side effects. Requesting a **retired** version does not error: Shopify returns HTTP 200 and silently serves the oldest supported version instead, disclosing the substitution only in the `X-Shopify-API-Version` response header. That is how the fleet spent three quarterly releases believing it was on `2025-01` while actually running `2025-10` — nobody chose that, and nothing said so. Only a version that does not exist *yet* fails loudly (404). So every response through `lib/shopify.js` runs `checkServedApiVersion`, which **warns to stderr and fires one deferred `notify()` per process, and never throws**: fall-forward hands back a newer *supported* version, so the run is degraded rather than broken, and hard-failing would take the unattended 8 AM pipeline — and the collectors that write the only copy of snapshot history — down over a condition the response survived. **Do not pin the next quarter early.** The version one quarter ahead is the release candidate, published *three* months before it stabilises, and it can change without notice — which is the same bug wearing a newer number.

**REST is legacy, but not on a clock.** The Admin REST API has been legacy since 2024-10-01 and is in maintenance mode; the hard rule ("must use GraphQL") binds **new public apps only**, and this is a custom app, so every REST endpoint the fleet uses still works on `2026-07`. Two carry an explicit deprecation notice and return `X-Shopify-API-Deprecated-Reason` on a live 200 — **`/products*`** (deprecated as of REST 2024-04) and **`/products/{id}/images/*`** (2025-01). Those are the endpoints to migrate to GraphQL first if REST ever gets a removal date. `productByHandle` is likewise deprecated-not-removed in `2026-07`; its replacement is **`productByIdentifier`**, not `product(handle:)`.

**Ad creative pipeline — two agents, two jobs.** `agents/ad-studio/` produces the **ad base**: a text-free, icon-free PLATE with the product rendered in-scene at ad scale and position, plus a safe-zone guide SVG and the claim-gated copy as text. The operator sets type and icons onto it in Photoshop. A throwaway **comp** is derived from each Meta plate so a human can see the intent — it is a picture of what the ad could be, never the ad. `agents/creative-packager/` produces **placement crops from an already-approved master**; that job is unchanged.

**Why plate-first.** Ad Studio used to bake finished ads and gate them hard on text. Chasing 100% text accuracy from an image model was a losing game — most expensively on 9:16, where Meta draws UI over the top ~14% and bottom ~20%, every layoutBrief runs a headline to the frame edge, and the model fills the frame whatever the prompt says (measured: 6 of 6 attempts failed at 3 paid attempts each). Moving type to Photoshop dissolved that: a plate has no copy to misplace, so 9:16 renders first-attempt and the safe zone ships as `guide-<ratio>.svg` instead of as three failed renders.

**Where strictness lives now.** **TWO copy gates, different questions, neither substituting for the other.** `claims.js` asks *can this be traced to a source we hold?* — an unsourced factual claim stops the run before anything renders, no override. It holds four sources — `pdp`, `catalog`, `brandKit`, `reviews` — plus a fifth, `giveaway`, that exists ONLY while a giveaway's Entry Period is open. That fifth one is the plain text of the **published** Official Rules and nothing else: `lib/giveaway-claim-source.js` uses `config/giveaway.json` purely to cross-check that the entry-open and entry-close calendar dates literally appear in the rules, and **throws rather than picking one** when they disagree. Folding the config's dates into the searchable body instead would let a writer cite a deadline the published rules contradict *as sourced evidence* — the claim gate defeated through its own front door. Adding a source is never relaxing matching: a giveaway claim absent from the rules is rejected exactly as before, and outside the Entry Period `sourceId: "giveaway"` fails as an unknown source. `health-claims.js` asks *is a COSMETIC allowed to say it at all?* and is equally hard: no disease name, no drug or prescription reference, no heal/cure/treat/prevent, no clinical or FDA backing, in any zone of any format. A **verbatim customer review passes the first and can still fail the second** — that is exactly what happened on 2026-08-16, when a correctly-sourced Judge.me quote ("tried prescription strength lotions, steroids... to no avail. Until Real Skin Care") sailed through sourcing. "It came from a review" is not a defence: the FTC holds an advertiser responsible for claims an endorsement *conveys*, and the FDA treats marketing material including testimonials as evidence of intended use, which is what turns a cosmetic into an unapproved drug. Reviews carrying such language are also withheld from the copy writer up front (`selectQuotableReviews`), because detection without prevention burns retries. **The same withholding now covers `data/context/personas.json`**, which is copy input read by four agents: the generated 2026-07-27 file named steroids, prescriptions and eczema in every copy-facing field of persona `p1` — the top-ranked one, so the *default* angle — which meant the default creative brief was seeded with the language this gate exists to reject. `lib/voice-of-customer.js`'s `sanitizePersonas` removes a violating angle (or the whole persona, when its own name or summary is the violation) at BOTH ends: when `agents/voice-of-customer` writes the file, and again when `creative-packager`, `ad-studio` and `ad-brief` read it, because the file is regenerated monthly and a bad month must not reach a copy prompt. It removes, never rewrites — an LLM rewrite would be the agent inventing research — and `source_quotes` is never screened, because it is the evidence record and no consumer feeds it to a writer. **Product fidelity** (`verify.js`) is still a hard fail: the reference photographs go to the verifier and a bottle that contradicts them on shape, cap, label element order, printed graphics or base colour is rejected, because Photoshop cannot fix a wrong product. Photographic styling — lighting, gloss, shadow, crop — is explicitly never a mismatch; relaxing that rejects good renders at $0.13 a retry. **Stray text on a plate** is a hard fail too: you cannot remove pixels. Everything about the comp is advisory, including its 1-5 quality score, which feeds `run.json`'s `ranking[]` and the rolling baseline in `data/reports/ad-studio/scores.jsonl`. `ok: true` means checked, not good.

**Second generative passes: what the rule actually protects.** The rule was "never feed a render back in", from a probe where a second pass shifted ingredient photos one row against their captions — jojoba captioned as coconut oil. The real hazard is **image/label pairing drift on an artifact that ships**. The comp pass is allowed because it violates neither half: the plate it derives from is already verified and is not modified, the comp is throwaway, and a plate carries no icons or captions for anything to drift against. Do not read this as permission to second-pass a shipping artifact. Note the consequence: **the image/label pairing check is now dormant** — nothing renders paired imagery any more. It is intact and tested, and fires again the moment a format does.

**`--formats` is required.** The default run is one format, one variation, all three Meta placements. Demand Gen plates are opt-in (`--targets all`). **`--flexible` builds one Meta 3-2-2 flexible ad** — 3 plates from 3 distinct formats at ONE ratio, plus 2 primary texts and 2 headlines from a second gated copy call — because twelve combinations sharing a single learning pool is what lets a $30/day campaign exit the learning phase at all (three ad sets ≈ 28 entries/week each, under Meta's ~50; consolidated ≈ 84). It refuses any argument set that would silently yield a different structure, and it writes a manifest only — **nothing in this repo creates, edits or launches anything on Meta.** The fleet's image-generation model IDs in `config/creative-models.js` are the **GA** releases, `gemini-3-pro-image` and `gemini-3.1-flash-image` — verified 2026-08-14. Do not reintroduce the `-preview` suffixes. `data/creatives/` has a **hard disk budget** (`lib/creatives-budget.js`), enforced automatically at the end of every Ad Studio run — "purge as we go", because a budget that waits for someone to remember a script is not a budget and this project has already lost four days of cron to a full disk. The ceiling is 10 GiB locally and **4 GiB on the production server**, set as `CREATIVES_BUDGET_BYTES` because that box has ~9.9 GB free of 24 GB and a ceiling above the free disk can never fire before the disk fills. It is resolved from `process.env` first and then from `.env` (`configuredBudgetBytes()`), so the paths that run unattended — the weekly cron sweep, which never sources `.env`, and a hand-run agent, whose `loadEnv()` deliberately keeps `.env` out of `process.env` — get the server's ceiling rather than the local default. Purge is tiered, cheapest loss first, and stops the moment the total fits: (1) rejected Ad Studio frames past a 7-day grace, (2) Ad Studio images from runs older than 14 days, (3) Creatives-tab session images idle 30+ days. **JSON is never deleted at any tier** — a run stays explicable after its pixels are gone — and the run just written is never eligible. When nothing further can be freed it says so rather than reporting success. `npm run creatives-budget -- --apply` runs the same sweep by hand (dry by default) and is scheduled on the server, because the Creatives tab fills the same directory without ever calling the agent. The older age-only `scripts/prune-ad-studio.mjs` still exists for deep pruning past 90 days. See `agents/ad-studio/README.md`.

## Data Layout Conventions

- `agents/<name>/index.js` — one agent per directory. Read the header docstring for usage.
- `lib/<name>.js` — flat namespace of shared libraries (Shopify, GSC, GA4, notify, posts helpers, retry, etc.). Subdir `lib/amazon/` for the SP-API client.
- `data/posts/<slug>/` — per-post intermediates: `content.html`, `meta.json` (Shopify article IDs, target keyword, `needs_rebuild` flag, `shopify_status` — see the publish-state note above; `blocked_resolution` when `blocked-post-resolver` has written off a verdict), `editor-report.md`, `answer-first.md`, `internal-links.md`, `backups/`, `content-refreshed.html` (queued).
- `data/snapshots/{gsc,ga4,clarity,shopify,google-ads}/YYYY-MM-DD.json` — daily metric snapshots. `data/snapshots/bing/` is the one exception to "one file, one day": Bing's API takes no date parameter and returns its whole ~6-month window on every call, so each file is a full history stamped with the day it was **collected**, written **weekly** from the Sunday block of `scheduler.js` (Bing's own data refreshes weekly — `GetQueryStats` returns 26 dates across 177 days, so a daily job would write six duplicate files). Its `coverage` block records that query/page rows are a weekly sample capped at 100 rows per date; those totals are deliberately far below the site totals and must never be reconciled against them. Bing itself is ~28 clicks/month and $0 revenue — the feed is kept because it is the only query-level view of the index **DuckDuckGo** serves from, and DDG converts new customers at 2.88% vs Google organic's 0.60%. The foundation for any outcome-attribution work. **Gitignored — written by cron on the server, never synced to your checkout.** A local checkout will look empty or months out of date; that is normal and is *not* evidence the collector is broken. To judge feed health, check the server (`ssh root@137.184.119.230 'ls -t ~/seo-claude/data/snapshots/<feed> | head'`), never the local tree. A zero-order day in `shopify/` is usually a real zero-order day — the store averages ~0.5 orders/day.
- `data/reports/<agent>/...` — per-agent run output. `latest.json` for dashboard consumption when present.
- `data/reports/seo-impact/latest.json` — the per-cluster **attributed** revenue every $0-cluster decision reads, through `lib/cluster-hold.js`'s `loadClusterHold` and nothing else. Its `window` block is what the corroboration window is derived from. **Directional only** — never hold, kill or deprioritise a cluster on this file alone; it must be corroborated against `data/snapshots/shopify/`. **Gitignored — written on the server**, so a local checkout holds nothing and says so; check the server before concluding the hold is broken.
- `data/context/feedback.md` and `data/context/writer-standing-rules.md` — agent guidance (see closed-loop feedback above).
- `data/context/voice-of-customer.md`, `data/context/personas.md`, `data/context/personas.json` — voice-of-customer research for the skin cluster, written monthly by `agents/voice-of-customer`. Headings are stable so the files stay greppable; every entry carries an evidence count and a verbatim quote. `personas.json` is rank-ordered — `creative-packager` reads `personas[0].angles[0]` as its default angle instead of the competitor reference ad's `messagingAngle`, where "first" means the first entry that survives the health-claim withholding described above (order is never rearranged, only filtered).
- `data/context/operator-angles.json` — **the operator's overlay on that research, and the only correct way to change an angle.** `personas.json` is regenerated monthly, so hand-editing it does two wrong things: the edit silently reverts on the next run, and authored copy becomes indistinguishable from mined evidence inside the file every downstream reader treats as evidence. The overlay retires angles by id and adds operator-authored ones (`authored: true`), and is **never written by an agent**. It is applied at LOAD by all five readers of `personas.json` — `ad-brief`, the dashboard's ad-brief route, `ad-studio`'s non-brief path, `creative-packager`'s `loadPersonas`, and `demand-miner`'s `realApplyPersonaOverlay` — always BEFORE `sanitizePersonas`, so an authored angle faces the same health-claim gate as a mined one. A reader that skips it serves retired copy and hides the replacement: that is what happened between 2026-08-18 and 2026-08-21, when angle **p2a2** ("125+ chemicals a day") was retired for citing EWG's **2004** figure of 126 — which EWG's own 2023 re-run revised **DOWN to 112**, so the angle was both stale and backwards on the trend — and replaced by authored **p2a4**, built on the real figure (`brand-kit.json`'s `category_ingredient_load`: 12 products a day, *as many as* 112 unique chemical ingredients, EWG / Morning Consult, 2,200 U.S. adults, 2023). Two of the (then four) readers never saw either change. `demand-miner` was added as a fifth reader after that incident, wired correctly from the start rather than repeating the gap. Quote that figure with its hedge and timeframe intact, as an **ingredient-count contrast** against this catalogue's one-ingredient products — never as a toxicity or safety claim, which `health-claims.js` rejects and the source does not support.
- `.claude/skills/marketing-*/SKILL.md` — marketing tactics mined from video by `agents/marketing-learner`, each with provenance and a `## Falsified` section for tactics tested here that failed. **This is the source of truth.** `creative-packager` builds its ad-copy tactic menu and "Do not propose" blocklist by generating a projection from these files in memory at read time (`renderContextMirror(scanSkillInventory(...))`) — it does not read a committed copy. `data/context/marketing-tactics.md` is written locally for human browsing and is **gitignored**: committing a generated file made every pair of concurrent learner PRs conflict on it, and let git 3-way-merge it into content the generator would never emit.
- `data/context/demand-questions.{md,json}` — top-of-funnel demand questions, written monthly by `agents/demand-miner` after `voice-of-customer` in the same scheduler block; joins to `personas.json` on `stage` and `persona_id`. Not written when a run harvests zero questions — the previous artifact is left in place rather than overwritten with nothing.
- `data/reports/gsc-query-miner/impression-leaks.json` — structured GSC impression-leak feed (`{ generated_at, source, min_impressions, leaks }`), written on every `gsc-query-miner` run including empty ones, so a downstream staleness check can tell "ran, found nothing" from "did not run".
- `data/keyword-index.json` — single source of truth for which queries optimizers should target. Built by `agents/keyword-index-builder` (dispatched daily, self-paces to biweekly via `built_at`), merging GSC commercial intent + Amazon BA + Amazon SQP into `by_validation_source`. **~2,215 keywords across 9 clusters as of 2026-08-10, read by 15 agents.** **Gitignored — built on the server.** A local copy is usually months stale; check the server, not your checkout.
- `config/{site,competitors,ingredients,specificity-flags,ai-citation-prompts}.json` — durable site/business config.
- `data/archive/` — product imagery that cannot be recovered from anywhere else (destroyed originals, replaced PDP frames, non-reproducible AI-generated frames). Committed on purpose; see its README before adding or removing.
- `assets/digital/<slug>/` — source for the bundle PDFs. **Building and publishing are two scripts:** `build-digital-assets.mjs` renders, `upload-digital-assets.mjs --apply` publishes with hand-versioned filenames (Shopify creates a suffixed duplicate rather than overwriting). Images are addressed `image=<filename>`, never by gallery index — positional refs silently re-pointed at a different picture whenever a PDP was reordered.
- **Locally-generated run output must be archived out of a worktree.** `lib/archive-run-output.js` copies a finished run to the same path under the MAIN checkout (resolved via git's common dir), because gitignored output inside a worktree is *untracked* and `git worktree remove --force` deletes it — that is how a set of Ad Studio sample plates was destroyed on 2026-08-15. Wired into `agents/ad-studio` and `agents/creative-packager`, the two agents that run manually and whose local copy is the only copy. **Do NOT archive server-authoritative directories** (`data/snapshots/`, `data/reports/giveaway/`, `data/keyword-index.json`): cron owns those on the production box, a local checkout is *expected* to be empty or stale, and copying one out of a worktree plants a stale file in the canonical path where somebody later reads it as current. The test is not "is it gitignored" but "would this data exist anywhere else if this directory vanished".
- `.env` — credentials (excluded from git). Never commit.

**Importing an agent must not run it.** `agents/<name>/index.js` historically called `main()` at module scope, so `import`ing one executed the whole agent — live Shopify writes, paid API calls, `process.exit`. That is not hypothetical: a test that imported `meta-ab-tracker` ran it against live Shopify (PR #423). The consequence is structural, not just risky — as of 2026-08-22 the unguarded half of the fleet was **52 agents / 22,375 lines exporting exactly 0 symbols**, so none of it could be unit-tested, against 56 guarded agents exporting 212. That is why so much logic lives in `lib/` — extraction is the only way to make it testable, and CLAUDE.md already documents drift caused by copying rather than importing (`AWARENESS_LEVELS`).

Every entry point uses **`isDirectRun(import.meta.url)` from `lib/is-direct-run.js`** — one tested predicate, because four hand-rolled spellings had accumulated (two differing only in operand order) and two separate audit passes miscounted which agents were guarded as a result. **The failure modes are not symmetric.** A guard that wrongly says "imported" turns a scheduled agent into a silent no-op that still exits 0, which cron and the 5 AM digest both read as success — strictly worse than the hazard being fixed. So the predicate resolves symlinks before giving up, falls back to an exact string compare, and is verified against all three real invocation styles: `node agents/x/index.js` (how `scheduler.js` shells out), an absolute path (how crontab does), and `import()` (must be blocked). Roll guards out **ordered by how fast a mistake becomes visible** — hand-run agents first, then `scheduler.js`-dispatched ones (a missing digest row exposes a no-op within 24h), then crontab jobs — never by how dangerous the agent is.

## Code Review Checklist — any agent that writes LLM-generated post HTML

**These checks are `assertHtmlComplete` in `lib/html-output-guards.js`. Call it; do not hand-roll them.** They must throw (not warn) before the HTML is saved or pushed:

1. **`stop_reason === 'max_tokens'`** — output was cut at the token limit; the post is incomplete. **Throw, do not save.** The file will be truncated mid-tag and produce broken links when published.
2. **Unclosed `href` attribute** — regex `/href="[^"]*$/` on the HTML. Output truncated mid-link. **Throw, do not save.** Shopify auto-closes the broken tag into a malformed URL (e.g. `https://domain.com/blogs/news/best`) that 404s.
3. **Unclosed block tag** (`unclosedBlockTags`) — a `<p>`/`<li>`/`<h2>`… opened and never closed means the output was cut **mid-prose**, where checks 1 and 2 can both miss it: check 2 only fires when the cut lands inside an attribute, and check 1 only when the caller actually inspected `stop_reason`. This is the shape the tattoo-soap merge had. Validated against all 203 live articles — every one balanced, so a failure here is real.

All three must be fatal — truncated HTML on Shopify creates broken links that take a manual audit cycle to find, and a truncated *merge* silently overwrites a proven ranking page with a page that stops mid-sentence.

Current callers: `agents/blog-post-writer`, `agents/citation-finder`, `agents/content-remediator` (via `lib/content-revision.js`), `agents/cannibalization-resolver`, `agents/content-refresher`, `agents/technical-seo`, `agents/specificity-audit`, `agents/answer-first-rewriter`, `agents/collection-content-optimizer`. **An agent that generates article HTML and does not appear in that list is a gap, not an exemption.** Never substitute an LLM's own "the final section is complete" assertion for these — the editor made exactly that assertion about content cut off mid-word.

A 2026-08-22 audit of every local post intermediate and every Shopify article (269 files, 203 articles) found **3 truncated artifacts, none of them live**: the tattoo merge, a second merge from the same 2026-08-16 resolver run (`toothpaste-without-sls-…/content.html`), and a queued `content-refreshed.html` from 2026-07-06 — which is what put `content-refresher` on the list above; it ran at a flat `max_tokens: 8192` with no `stop_reason` check, the same defect. Live and draft Shopify articles were clean (0/203), so nothing truncated ever reached readers.

**The 2026-08-23 sweep of the remaining 13 HTML-generating agents settled which actually need this, and the answer was 4, not 13.** The distinction is *what the model returns*, not what the agent eventually writes:

- **Guarded** — the model's own output IS the HTML that ships: `technical-seo` (a collection-page rewrite that had **no truncation check of any kind**, not even `stop_reason` — the worst of the set, and collections are the pages that convert), `specificity-audit` (live product description), `answer-first-rewriter` (handed straight to cheerio's `replaceWith()` against a live article body), and `collection-content-optimizer` — where the guard is applied to the **`body_html` field**, not the raw response, because the response is a JSON envelope and a block-tag check against the envelope is meaningless.
- **Correctly NOT guarded** — the model returns something that is not HTML, and guarding it would throw falsely in production: `collection-creator`, `collection-linker`, `internal-linker`, `competitor-intelligence`, `product-optimizer` all return **JSON** (the `body_html` is assembled afterwards by deterministic code); `link-repair` returns **a URL**; `editor` returns **review prose**; and `faq-rewriter` returns **plain text** in a `QUESTION:/ANSWER:` envelope — the agent preserves the wrapping `<p>`/`<h2>` tags itself, so the model never emits a block tag.

The lesson worth keeping: "this agent writes `body_html`" is not the test. Read the call site and ask what the model returned.

Two of the JSON callers (`collection-linker`, `internal-linker`) silently `return []` when `JSON.parse` fails, so a truncated response there degrades to "no suggestions" rather than corrupt HTML — a real but different bug (silent degradation, not corruption), deliberately left alone.

## Product Imagery — two rules that have already cost real work

**Deleting a Shopify product image destroys the CDN file.** `DELETE /products/{id}/images/{id}.json` removes the underlying file, not just the product association — even for a `/files/` path. On 2026-08-12 three bundle photos were deleted from the foaming soap PDP and are unrecoverable (absent from the Files library, 404 on the CDN, no Wayback capture). **Download full-resolution to `data/archive/` before any destructive image call, and grep the repo first** — product images turn out to be embedded in live blog posts, Klaviyo flow scripts, and `assets/digital/image-map.json`. Prefer reordering or reattaching, which are reversible. A detached image can still return 200 for a while with its original `?v=` param; that is CDN lag, not survival.

**The theme scopes gallery images to variants two mutually exclusive ways.** In `sections/main-product.liquid`:

1. **Variant attachment** — set `hide_variants: true` on the template's `main` section. Attached media renders only for the selected variant; unattached media renders for all (this is how shared marketing frames work).
2. **alt-text `#` "gang" scoping** — images whose `alt` contains `#<token>`. **This path only runs when `hide_variants` is false.**

Before flipping `hide_variants` on any template, check whether that product's images carry `#` in their alt text. If they do it is already gang-scoped and the flag will break it. `scoped-gallery` and `bundle-landing` templates use the gang mechanism; the `landing-page-*` templates use variant attachment.

### Snapshot backups

`data/snapshots/` is the only copy of GSC/Clarity history past those APIs' retention windows (~16 months for GSC, shorter for Clarity) — it cannot be re-fetched once gone.

- **Offsite (authoritative):** `scripts/backup-snapshots-offsite.sh` runs on the **server**, Sundays 17:00 UTC via cron → DigitalOcean Spaces `rsc-backups/snapshots/`, keeps 12 weekly archives. Credentials are `SPACES_*` in `.env`; rclone is configured purely via `RCLONE_CONFIG_*` env vars, so there is no `rclone.conf` holding a second copy of the secret. Verifies the uploaded object's byte size against local before reporting success, then prunes.
- **Local working copy:** `npm run sync-snapshots` (rsync server→local, ~78 MB, ~3s). Direction is hardcoded and `--delete` is deliberately omitted — local accumulates as a superset so a server-side loss can't propagate. A launchd job runs it daily at 09:00.

### Deploy hygiene — backfills run AFTER `git pull`, never before

The `data/` tree contains tracked files (e.g. `data/posts/<slug>/meta.json`) that get modified in-place by backfill scripts. If you `git stash push` before pulling, those uncommitted updates land in stash and get forgotten. Run any data backfill **after** the pull — scripts are idempotent so re-running on top of fresh code is safe.

If `git pull` fails because of a dirty working tree:

```bash
ssh root@137.184.119.230 'cd ~/seo-claude && git stash push -m "pre-deploy <pr-id>" && git pull && git stash pop && pm2 restart seo-dashboard'
```

`git stash pop` is non-negotiable. If the merge can't reconcile, resolve manually. Never leave a stash dangling — `git stash list` should be empty (or near-empty) after a deploy.

**Never** `git stash --include-untracked` on the server — it destroys ALL untracked data files (queued performance items, draft posts, generated reports), not just conflicting ones. Delete specific files instead.
